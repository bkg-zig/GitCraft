## Zielarchitektur

```
Browser (HTTPS)
  ↓
Traefik (bkg_net, gc.eysho.info:443 → gc-gc-1:3000) [extern / Core]
  ↓
gc-web (Dioxus Fullstack, Port 3000)
  ├── Dioxus Server Functions (SSR + WASM Hydration)
  │     ├── GET /api/gc/dashboard     → Engine → TaskStore (SQLite WAL)
  │     ├── POST /api/gc/tasks        → Engine::create_task()
  │     ├── POST /api/gc/tasks/{id}/cancel|retry
  │     ├── DELETE /api/gc/tasks/{id}
  │     ├── POST /api/gc/tasks/clean
  │     ├── POST /api/gc/review       → review::run() → CodeGraph + rules.json
  │     ├── GET /api/gc/architecture  → codegraph::analyze() + architecture()
  │     └── GET /api/gc/llm/probe     → LlmClient::probe() → /models
  ├── Axum Internal API (Bearer Token auth)
  │     ├── POST /api/internal/goal/tasks   → Engine::create_task()
  │     └── GET  /api/internal/goal/tasks/{id} → Engine::get_task()
  └── Engine Scheduler (tokio background)
        └── run_one(task) → git::prepare_workspace()
              ↓
           SandboxRunner
             ├── Docker Network (gc-net-{task-id}, internal)
             ├── gc-proxy:local Container (Port 3128, GC_PROXY_ALLOW)
             │     └── gc-egress Network (external)
             └── gc-agent:local Container
                   └── Agent (gc | codex | claude) → /instructions/instructions.md
                         ↓ (on success)
                   git::commit_and_return_branch() → source repo

CLI (gc binary) / TUI (gc tui) / ACP (gc acp, stdio)
  └── init_engine() → gleiche Engine-Instanz

Code Vault: .gc/vault/vault.sqlite (FTS5, Snapshots, Artifacts)
```

**Proxy-Analyse:**
- Der interne `gc-proxy:local` Container (aus `src/bin/gc-proxy.rs`) ist ein nativer HTTP-CONNECT-Proxy
- Er ist **notwendig JA** — er implementiert die Netzwerkisolierung der Sandbox. Agent-Container kommunizieren nur über diesen Proxy mit definierten Domains (GC_PROXY_ALLOW). Ohne ihn: keine Egress-Kontrolle.
- Er ist kein Legacy-Workaround, sondern integraler Bestandteil der Sicherheitsarchitektur.
